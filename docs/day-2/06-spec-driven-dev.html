Spec-Driven Development

AI models are excellent at pattern completion and poor at mind reading. A spec is how you close that gap before you start building.

01

The Core Idea

Spec-driven development inverts the usual workflow: the specification becomes the source of truth, and code becomes a generated or verified secondary artifact.* GitHub's own tooling for this, spec-kit, describes the same inversion independently: you give the agent a high-level description of what you're building and why, and it generates the spec first, the plan second, code last.*

Why this matters more with AI assistants than it used to: AI models are excellent at pattern completion, and poor at mind reading.* A vague prompt like "add photo sharing to my app" leaves Claude guessing at what you actually meant. A spec gives it enough to match your intent instead of inventing one.

Worth knowing before you reach for this on every project: it works best on new, well-scoped work. One independent critique argues that on a large, already-existing codebase it mostly breaks down, planning can't eliminate the non-determinism of real development the way it promises to.* For an afternoon build in this workshop, that's rarely the constraint you'll hit.

02

The Checklist

A repeatable four-step framework, worth applying to your own project this afternoon, and one that independent teams building real spec-driven tools converge on in roughly the same shape.*

  1. 1

    Specify

    What should it do? Behavior, requirements, acceptance criteria, no implementation details yet. GitHub's spec-kit and AWS's Kiro both start in the same place, under names like requirements.md.*

  2. 2

    Plan

    How should you build it? Architecture, data models, interfaces. The spec declares intent; the plan declares constraints. This is also the step that resists automation the most, per one four-engineer team's year of running this loop with Claude Code: decomposing a spec into a plan needs a human's judgment about the codebase and the team, not just the model's.*

  3. 3

    Implement

    Small, validated increments, each one a testable piece of functionality, not one giant leap. That same team reported roughly a two-to-three-times increase in throughput over a year running this workflow, with headcount unchanged.*

  4. 4

    Validate

    Does the code actually meet the spec? If not: was the spec wrong, or the code? Either way, the spec stays the authority.

What makes step 1 actually work: a good spec is behavior-focused (what happens, not how), testable, unambiguous, and complete enough without over-specifying.* One practical rule of thumb: if there's only one reasonable way to read a requirement, don't add more detail. If there's more than one, that's exactly where to add clarification.*

A passing test only proves the code matches the spec, not that the spec was right in the first place.* Claude Code's own team makes a related point about validation generally: Claude stops when the work looks done, and without an explicit check to run, "looks done" is the only signal you get.* Neither of the real tools that implement this workflow treats validation as one closing step, either: GitHub's spec-kit and AWS's Kiro both check continuously between phases, through dedicated clarify/analyze commands or review gates, rather than saving it all for the end.*

One pitfall the checklist above doesn't cover: a spec that isn't updated when the code changes doesn't just become unused, it becomes actively misleading. An agent will follow it confidently even after it's stopped matching reality.* If you revise your project later today, revise the spec too.

03

Why This Connects to Skills

Specs, done well, act as modular building blocks Claude can work from directly, close to what a Skill is doing when it packages expertise for reuse.* A Skill is essentially a pre-written spec for a kind of task you'll do again. Once you've written a spec once, the checklist above is what makes it repeatable the next time.

If this clicks for you, GitHub's spec-kit and AWS's Kiro are two real, free tools built entirely around this loop, worth a look after the workshop.**
